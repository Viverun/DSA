## 1.10 Introduction to Recursion

---

### What Is Recursion?

Recursion is a technique where a function solves a problem by calling **itself**, on a smaller version of the same problem, until it hits a point simple enough to answer directly without any further calls. That "simple enough to answer directly" point is called the **base case**, and it's what eventually stops the chain of calls.

At its core, recursion is a way of expressing "solve this big problem by solving a slightly smaller version of the same problem, and building the answer from that." It's a genuinely different way of thinking about repetition compared to the loops you've been using so far (1.5, 1.6) — instead of a variable being updated pass after pass, the function calls a fresh copy of itself, and each copy handles one small piece of the overall task.

---

### Anatomy of a Recursive Function in Python

Every working recursive function needs exactly two pieces:

1. **A base case** — a condition where the function stops calling itself and just returns a direct answer.
2. **A recursive case** — where the function calls itself again, working on a smaller or simpler version of the original input, moving it *toward* the base case.

```python
def recursive_function(n):
    if <base case condition>:
        return <direct answer>
    # do some work
    recursive_function(<smaller version of n>)   # the recursive call
```

If you're ever unsure whether a recursive function you've written is correct, check both pieces explicitly: is there a base case that's actually reachable, and does every recursive call move the input closer to it? Missing either one is the root cause of nearly every recursion bug you'll encounter.

---

### Worked Example: Printing "Hey, Striver!" N Times

Let's build the simplest possible recursive function — printing a message `n` times, using recursion instead of a loop.

```python
def print_n_times(n):
    if n == 0:              # base case — stop here
        return
    print("Hey, Striver!")
    print_n_times(n - 1)    # recursive case — smaller version of the problem

print_n_times(5)
```
**Output:**
```
Hey, Striver!
Hey, Striver!
Hey, Striver!
Hey, Striver!
Hey, Striver!
```

Notice the shape of the logic: each call handles printing **once**, then hands off the remaining `n - 1` prints to a fresh call of itself. `n` shrinks by 1 every single call, guaranteeing it eventually reaches `0` — the base case — and the chain of calls stops.

---

### The Base Case — Why It's Non-Negotiable

Here's what happens if you remove the base case entirely:

```python
def print_forever(n):
    print("Hey, Striver!")
    print_forever(n - 1)     # no base case — this never stops!

print_forever(5)
```

This function will keep calling itself indefinitely — `n` will go `5, 4, 3, 2, 1, 0, -1, -2, ...` forever, since nothing ever tells it to stop. Eventually, this crashes the program (details on exactly how, in Python's case, a few sections below). **Every recursive function must have a base case that is actually reachable from every possible starting input** — not just a base case that exists somewhere in the code, but one the recursive calls are guaranteed to eventually hit.

---

### The Call Stack — What's Actually Happening in Memory

Every time a function calls another function (including calling itself), Python doesn't just "jump" to the new call and forget where it came from — it needs to remember where to *return to* once that call finishes, along with all of that call's local variables. This bookkeeping happens on something called the **call stack**: each function call gets pushed onto the stack as a new "frame," and is only popped back off once that specific call fully completes (hits a `return`, explicit or implicit).

For a recursive function, this means every single recursive call adds its own frame to the stack — and none of those frames get removed until the base case is finally hit and the chain of calls starts unwinding back to the top.

For `print_n_times(5)`, the stack builds up like this before anything starts returning:

```
print_n_times(5)
  → print_n_times(4)
      → print_n_times(3)
          → print_n_times(2)
              → print_n_times(1)
                  → print_n_times(0)   ← base case hit here, this call returns immediately
```

Once `print_n_times(0)` returns, control goes back to `print_n_times(1)`, which itself has nothing left to do after its recursive call, so it returns too — and this unwinding continues all the way back up to the original `print_n_times(5)` call, which then finally finishes as well.

---

### Tracing the Recursion Tree

A useful mental (or literal, on paper) exercise: draw out every call and what happens inside it. For `print_n_times`, since each call only makes exactly one further call, the "tree" is really just a straight chain — but this changes dramatically once you get to recursive problems that make **multiple** recursive calls per level (like tree traversals or Fibonacci, later in this sheet), where the "tree" genuinely branches.

A small but genuinely illuminating variation — moving the `print` statement to happen *after* the recursive call instead of before:

```python
def print_after_call(n):
    if n == 0:
        return
    print_after_call(n - 1)
    print(n)

print_after_call(5)
```
**Output:**
```
1
2
3
4
5
```

Compare this carefully to the very first example. Nothing about the *calls themselves* changed — `n` still goes `5 → 4 → 3 → 2 → 1 → 0` on the way down. What changed is *when* each call does its printing relative to its own recursive call: printing **before** recurring prints in the order the calls are made (5, 4, 3, 2, 1); printing **after** recurring prints in the order the calls **return and unwind** (1, 2, 3, 4, 5). This single idea — that code placed before vs. after the recursive call executes at completely different points in the call/return sequence — is the foundation for a huge number of recursive patterns you'll build later in this sheet.

---

### Python's Recursion Limit — The Most Important Python-Specific Gotcha

Here's something you need to know before writing much more recursive code: **Python enforces a maximum recursion depth**, and it's considerably shallower than you might expect — the default limit is **1000** nested calls.

```python
def print_n_times(n):
    if n == 0:
        return
    print_n_times(n - 1)

print_n_times(2000)
```
**Output:**
```
RecursionError: maximum recursion depth exceeded
```

This isn't a bug in your code in the usual sense — it's a deliberate safety limit Python enforces to prevent a runaway recursive function from crashing the entire interpreter by exhausting real memory. But it means that **recursive solutions that would work fine in a language like C++ can hit this ceiling in Python long before running out of actual system memory** — this is a genuinely important difference to keep in mind as you write recursive solutions throughout this sheet, especially once input sizes grow large.

### Checking and (Carefully) Raising the Limit

```python
import sys

print(sys.getrecursionlimit())    # 1000, by default

sys.setrecursionlimit(3000)         # raise it, if you genuinely need to
```

**Use this carefully, not as a default habit.** Raising the recursion limit doesn't add real memory — it just tells Python to allow deeper recursion before stopping you, and a sufficiently deep recursion can still crash the program with an actual segmentation fault if it runs past what your system can genuinely handle. Treat `sys.setrecursionlimit()` as an escape hatch for specific, deliberate cases (and something you'll sometimes need to do on judges/environments for legitimately deep recursive algorithms) — not a substitute for considering whether an iterative approach is more appropriate for a given problem size.

---

### No Tail-Call Optimization in Python

Some languages automatically optimize a specific recursive pattern called **tail recursion** — where the recursive call is the very last thing a function does, with nothing left to compute after it returns — turning it internally into something as memory-efficient as a loop, reusing the same stack frame instead of piling up new ones.

**Python deliberately does not do this**, even when your recursive function is written in a perfectly tail-recursive style. Every recursive call in Python still consumes its own stack frame, no matter how the function is structured. This is a genuine, permanent language design choice (not a missing optimization Python might add later) — so writing your recursion in a "tail-recursive shape" won't save you from the recursion limit or the memory overhead the way it would in some other languages. If a recursive function needs to handle genuinely large depths, converting it to an iterative loop is often the real solution in Python, not restructuring the recursion.

---

### Advantages of Recursion

- **Simplifies code for naturally recursive problems.** Tree traversals, factorials, Fibonacci-style sequences, and divide-and-conquer algorithms are often dramatically shorter and clearer written recursively.
- **Matches the natural structure of certain problems.** Some problems are just inherently defined in terms of smaller versions of themselves — recursion lets your code mirror that structure directly.
- **Foundational for major algorithm families.** QuickSort, MergeSort, binary search variants, backtracking, and dynamic programming (all covered later in this sheet) are built on recursive thinking.

---

### Disadvantages of Recursion (With Python's Specifics in Mind)

- **Real memory overhead per call.** Every recursive call keeps its own frame on the stack until it returns — for deep recursion, this adds up.
- **Python's shallow default recursion limit (1000)** makes this constraint bite sooner than in many other languages, and needs active management (`sys.setrecursionlimit()`) for legitimately deep recursive solutions.
- **No tail-call optimization**, meaning Python can't quietly rescue you from deep recursion the way some other languages can — depth genuinely costs stack frames every time.
- **Generally slower than an equivalent loop**, because function call overhead (setting up and tearing down each frame) is real cost that a loop doesn't pay.
- **Harder to trace and debug**, especially once recursive calls branch into multiple calls per level rather than the simple single-chain examples here.

## Cheat Sheet — 1.10 Introduction to Recursion

| Concept | Key Idea |
|---|---|
| Recursion | A function calling itself on a smaller version of the problem |
| Base case | The condition that stops further recursive calls — must be reachable |
| Recursive case | Where the function calls itself, moving the input toward the base case |
| Call stack | Each call gets its own frame; frames are removed only as calls return |
| Code before the recursive call | Runs in call order (top-down) |
| Code after the recursive call | Runs in return/unwind order (bottom-up) |
| Default recursion limit | 1000 (check with `sys.getrecursionlimit()`) |
| Raising the limit | `sys.setrecursionlimit(n)` — use deliberately, not by default |
| Tail-call optimization | Not present in Python — every call still costs a stack frame |

## Common Pitfalls to Avoid

- **Writing a recursive function with no base case, or a base case that's unreachable** from some possible inputs (e.g., only handling `n == 0` but calling with a starting value that skips past it, like counting by 2s from an odd number).
- **Assuming recursion in Python can go as deep as it could in C++.** Python's default 1000-call limit will stop you well before you'd hit an actual memory ceiling.
- **Raising `sys.setrecursionlimit()` as a blanket fix without considering whether the recursion itself should be rewritten iteratively** for genuinely large inputs.
- **Expecting tail-recursive-style code to be automatically optimized.** It isn't, in Python — restructuring recursion to look tail-recursive doesn't reduce its stack cost here.
- **Confusing "before the recursive call" and "after the recursive call" placement.** This single choice determines whether your output reflects call order or return order — trace through a small example by hand if you're ever unsure.
