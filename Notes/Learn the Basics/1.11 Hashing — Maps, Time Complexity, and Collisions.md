# Chapter I — Learn the Basics
## 1.11 Hashing — Maps, Time Complexity, and Collisions

---

### The Problem Hashing Solves

Consider this scenario: you have an array `[1, 2, 1, 3, 2]`, and a set of queries `[1, 3, 4, 2, 10]` — for each query, you need to report how many times that number appears in the array.

```python
arr = [1, 2, 1, 3, 2]
queries = [1, 3, 4, 2, 10]
# Expected answers: 2, 2, 0, 2, 0
```

---

### Brute Force: Counting Frequencies with a Loop

The most obvious approach, using what you already know: for every query, scan the whole array and count matches.

```python
def count_occurrences(arr, query):
    count = 0
    for num in arr:
        if num == query:
            count += 1
    return count

arr = [1, 2, 1, 3, 2]
queries = [1, 3, 4, 2, 10]

for q in queries:
    print(count_occurrences(arr, q))
```
**Output:**
```
2
2
0
2
0
```

**Time complexity:** scanning the array once is O(N). Doing that for every one of `Q` queries brings the total to **O(Q × N)**. This sounds fine until the numbers get large — with `Q` and `N` both around `10⁵`, that's roughly `10¹⁰` total operations. Recalling section 1.8's discussion of judge time limits (and being appropriately conservative for Python), `10¹⁰` operations is nowhere close to feasible within a normal time limit. This is exactly the kind of situation hashing is designed to fix.

---

### The Optimized Approach: Pre-Storing and Fetching

The core idea behind hashing, stated simply: **do the expensive work once, upfront, and then answer every query with a cheap lookup.** This breaks into two steps:

1. **Pre-storing** — scan the array once, and record how many times each value appears.
2. **Fetching** — for each query, look up the pre-recorded count directly, instead of re-scanning anything.

---

### Number Hashing with a Python List

If you know the values in your array stay within a reasonable, bounded range, you can use a plain Python list as a frequency table — mirroring the classic "hash array" approach directly:

```python
arr = [1, 3, 2, 1, 3]
max_val = 12   # assume we know values won't exceed this

hash_arr = [0] * (max_val + 1)
for num in arr:
    hash_arr[num] += 1

queries = [1, 4, 2, 3, 12]
for q in queries:
    print(hash_arr[q])
```
**Output:**
```
2
0
1
2
0
```

**Pre-storing** happens in the first loop (`hash_arr[num] += 1` for every element) — this is **O(N)**. **Fetching** is then just a direct index lookup per query — **O(1)** each. Total complexity: **O(N + Q)** instead of O(N × Q) — a massive improvement, and the entire reason hashing matters.

---

### The Limitation: What About Very Large Numbers?

This list-based approach has an obvious weak point: it requires knowing the maximum possible value upfront, so you can size the list correctly. If array values could be as large as `10⁹`, you'd theoretically need a list with a billion slots — which is completely impractical, both in memory and in the time it takes just to create and initialize it.

**This is where Python's `dict` becomes the real answer, and it resolves this limitation entirely.** Unlike a fixed-size list, a dictionary only stores entries for keys that actually appear — there's no need to know the maximum value in advance, no wasted space for values that never show up, and no upper bound on how large a key can be:

```python
from collections import Counter

arr = [1, 2, 3, 1, 3, 2, 12]
freq = Counter(arr)

queries = [1, 2, 3, 4, 12]
for q in queries:
    print(freq[q])
```
**Output:**
```
2
2
2
0
1
```

This works identically whether your array contains values up to `12` or up to `10⁹` — the size-limitation problem that a fixed array runs into simply doesn't exist here. This is the standard, idiomatic way to solve number-hashing problems in Python, and you should reach for it by default rather than pre-sizing a list, unless you have a specific reason to want array-style indexing.

### Character Hashing — Python Makes This Simpler

The character-hashing version of this problem: given a string, count how many times each character appears, then answer queries against those counts.

If you wanted to mirror the array-based approach directly, Python's `ord()` function gives you a character's underlying code point (the direct equivalent of the ASCII-casting trick used in some other languages):

```python
s = "abcdabehf"
hash_arr = [0] * 26   # assuming lowercase a-z only

for ch in s:
    hash_arr[ord(ch) - ord('a')] += 1

for q in "agchb":
    print(hash_arr[ord(q) - ord('a')])
```
**Output:**
```
2
0
1
2
1
```

`ord('a')` is `97`; subtracting it from any lowercase letter's code point maps `'a'` through `'z'` down to `0` through `25` — exactly enough to index a 26-slot list.

**But here's an important, genuinely Python-specific consideration:** this array-indexing trick assumes your text is restricted to a small, known character range (lowercase letters, or ASCII more broadly). Python strings are **Unicode-native** — they can contain characters from virtually any writing system, emoji, symbols, and so on, with code points ranging far beyond what a small fixed-size list can practically index. The array-based approach doesn't generalize well the moment your input isn't guaranteed to be plain ASCII.

The far simpler, more robust solution — exactly the same tool used for number hashing above:

```python
from collections import Counter

s = "abcdabehf"
freq = Counter(s)

for q in "agchb":
    print(freq[q])
```
**Output:**
```
2
0
1
2
1
```

This works correctly no matter what characters actually appear in the string — no assumptions about lowercase-only, no fixed-size array, no `ord()` arithmetic required. Unless you have a specific reason to want array-based character indexing, this is the version to default to.

---

### A Crucial Difference: Missing Keys Raise `KeyError`, Not 0

This is worth stating explicitly, because it trips up people coming from languages where a map automatically returns a default value (like `0`) for a key that's never been touched. **Python's plain `dict` does not do this:**

```python
d = {}
d[5] += 1   # KeyError: 5
```

Accessing or incrementing a key that doesn't exist yet raises an error — Python won't silently assume you meant `0`. There are three clean, idiomatic ways to handle this, and you'll use all three regularly:

```python
# Option 1: .get() with an explicit fallback — read-only, doesn't fix a missing key permanently
d = {}
print(d.get(5, 0))   # 0 — safe, no error

# Option 2: defaultdict — missing keys are auto-initialized on first access
from collections import defaultdict
d = defaultdict(int)
d[5] += 1              # works — starts from 0 automatically
print(d)                 # defaultdict(<class 'int'>, {5: 1})

# Option 3: Counter — purpose-built for exactly this frequency-counting use case
from collections import Counter
c = Counter()
c[5] += 1               # works — same auto-defaulting behavior, specialized for counting
print(c)                  # Counter({5: 1})
```

For frequency-counting problems specifically (which is most of what this topic covers), `Counter` is almost always the cleanest choice — it's purpose-built for exactly this.

### Time Complexity of `dict` Lookups

As covered in sections 1.8 and 1.9: Python's `dict` (and by extension `Counter`, which is a `dict` subclass) gives **O(1) average-case** time for both storing and fetching values, regardless of how many entries it holds. This holds true whether your keys are small numbers, large numbers, or strings — the underlying mechanism (covered next) doesn't care about the magnitude of the key, only about computing a consistent hash from it.

Worth noting for completeness: Python has only **one** general-purpose dictionary type. Some languages draw a distinction between a tree-based "sorted map" (O(log n) operations, keys kept in sorted order) and a genuine hash-based map (O(1) average, no ordering guarantee). Python's `dict` is always the hash-based kind — if you need sorted key order, you sort explicitly with `sorted(d.items())` when you need it, or reach for the third-party `sortedcontainers.SortedDict`, both already covered in section 1.9.

### How Hashing Actually Works Under the Hood: The Division Method

It's worth understanding, at least conceptually, what a hash table is actually doing internally — this is exactly the kind of thing interviewers like to probe on.

Say you have an array `[2, 5, 16, 28, 139]`, and you're told you can't use a lookup structure larger than size 10. The **division method** handles this by taking each value modulo 10, and using that remainder as the index instead of the raw value itself:

```python
arr = [2, 5, 16, 28, 139]
table_size = 10
hash_table = [0] * table_size

for num in arr:
    hash_table[num % table_size] += 1

print(hash_table)
```

This compresses an unbounded range of possible values down into a small, fixed number of "buckets" — which is exactly the strategy real hash tables use internally, just with far more sophisticated hash functions than a simple modulo.

**Python exposes this same underlying idea directly through the built-in `hash()` function:**

```python
print(hash(42))       # some large integer
print(hash("abc"))     # some large integer
print(hash(3.14))       # some large integer
```

Internally, Python's `dict` computes something like `hash(key) % internal_table_size` to decide roughly where an entry should live — the same core principle as the manual division-method example above, just with a much more carefully designed hash function behind it.

**A genuinely important, directly related fact — tying back to section 1.7's mutability discussion:** `hash()` only works on **immutable** objects. This is exactly why lists, dicts, and sets can never be used as dictionary keys or set elements — they're mutable, and hashing something whose contents can change afterward would break the entire structure (the item could end up in the wrong "bucket" the moment it changed).

```python
d = {[1, 2]: "value"}   # TypeError: unhashable type: 'list'
```

If you ever need to use a list-like collection as a key, convert it to a `tuple` first — tuples are immutable and therefore hashable:
```python
d = {(1, 2): "value"}   # works fine
```

---

### Collisions and Chaining

What happens when two different values land in the same bucket — like `28`, `38`, `48`, and `18` all reducing to remainder `8` under modulo 10? This is called a **collision**, and the classic way to resolve it is **chaining**: instead of storing a single count at that bucket, you keep a small list of everything that landed there, and search within that list when needed.

You don't need to implement this yourself — Python's `dict` handles collision resolution internally (using a different but conceptually related technique called open addressing). The practical takeaway is about **worst-case behavior**: if a huge number of your keys happen to collide into the same bucket, individual lookups degrade from the expected O(1) toward O(n), since the structure has to search through everything sharing that bucket. This is rare in practice with Python's dict — its hash function is designed specifically to spread keys out evenly — but it's the reason "average case O(1), worst case O(n)" is the technically correct way to describe dictionary performance, rather than claiming O(1) unconditionally.

## Cheat Sheet — 1.11 Hashing

| Task | Code |
|---|---|
| Pre-storing with a fixed-range array | `hash_arr = [0] * (max_val + 1)` then `hash_arr[x] += 1` |
| Frequency counting, any range of values | `from collections import Counter; freq = Counter(arr)` |
| Character-to-code-point mapping (if needed) | `ord(ch)` |
| Safe lookup with a default | `d.get(key, 0)` |
| Auto-defaulting dictionary | `from collections import defaultdict; d = defaultdict(int)` |
| Underlying hash of an object | `hash(x)` (immutable types only) |
| Using a list-like key | convert to `tuple` first |
| Sorted key iteration | `sorted(d.items())` |

## Common Pitfalls to Avoid

- **Reaching for a fixed-size list when values could be very large or unbounded.** Use `dict`/`Counter` instead — there's no size-planning problem to solve.
- **Assuming `d[key]` returns `0` for a missing key, the way it might in some other languages' map types.** Plain Python `dict` raises `KeyError` — use `.get()`, `defaultdict`, or `Counter` when a default is what you actually want.
- **Assuming character hashing with a fixed 26- or 256-slot array generalizes to any text.** Python strings are Unicode-native; a small fixed range only holds if you're certain the input is restricted to ASCII/lowercase — `Counter` sidesteps this entirely.
- **Trying to use a list, dict, or set as a dictionary key.** These are mutable and therefore unhashable — convert to a `tuple` (for list-like data) if you need this.
- **Overstating dict performance as unconditionally O(1).** It's O(1) *average case* — worst-case degradation to O(n) is possible under heavy collisions, even though it's rare in practice.
